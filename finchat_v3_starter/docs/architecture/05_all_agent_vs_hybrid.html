What if every step were an agent?

A design comparison for leadership: the hybrid approach we run today, against a version where each step is its own model-driven agent. Based on the real code in backend/finchat_agents; figures marked estimate are not measured.

The principle: models decide, code guarantees. We use agents where the task needs language understanding or judgment (classify, write SQL, phrase the answer, explore complex questions). We use code where the answer must be the same every time (access, safety, numbers, storage).

1. Today: a hybrid

A simple data question uses three model calls. Complex questions switch to a supervisor agent that coordinates specialist agents in a loop.

2. The alternative: every step an agent

Each box becomes a model call with its own prompt. It looks modular, and it is, but the whole chain is now probabilistic and sequential.

3. The problems, in order of impact

IssueWhy it happensWhat it means
LatencyEach agent is a model call of about 2 to 4 s. Our route call alone measures about 3 s. Fourteen in a row add roughly 30 to 55 s (estimate) on top of today's 20 to 30 s.Users wait about a minute for a one-line answer.
Accuracy compoundsEvery model step has some chance of a wrong hand-off. If each of 12 model steps were 97% reliable, the chain would be right about 69% of the time (0.97 to the power 12). Code steps stay at 100%.More agents means more places for a quiet mistake.
Security and guardrailsRules written as prompts can be argued around by a clever question or a poisoned table value. In code, the SQL check, access check and read-only limit hold whatever the model says.A model must never be the last line of defence for finance data.
Numbers and trustThe number check works because it is independent of the model that wrote the answer. If a model does the checking, the same blind spot can pass the same wrong number.Finance users need every figure traceable to a query.
CostEach agent resends its instructions and the shared context, so token use grows with every step (indicatively several times today's). Prompt caching softens this, but not the call count.Higher cost per question for the same value.
Testing and repeatabilityCode steps are unit-tested and give the same output for the same input. Fourteen model steps take a different path each time, so a regression is harder to find and prove.Release confidence drops.
Failure handlingEvery agent can time out, hit a rate limit or return malformed output. Fourteen hand-offs need fourteen retry and fallback paths, and one throttled call stops the chain.Lower availability.
Audit and complianceAuditors ask who allowed a query and why. A deterministic rule has one clear answer. A model decision needs a transcript and still may not repeat.Harder to certify.

5. Agent by agent

For each step of the all-agent design: what the agent would do, how it can fail, and what our code does instead.

1. Context agent Code in our design
As an agent
Decides which earlier turns, user habits and summaries to read, then reads and summarises them.
Where it may go wrong
Reads too little (loses the thread of the conversation) or too much (slow, noisy prompt). Could ask for another user's turns. Summaries can drop an entity or period.
Why that is not good
The inputs are fixed: this conversation, this user. Judgment adds seconds and a privacy risk with no gain.
What our code does
Reads conversation, last turns and user habits in parallel with fixed queries filtered on the user id; habits cached for 10 minutes.
How that helps
About 0.7 s total (measured). Another user's data cannot be read, because the user id is in the query, not in a prompt.
2. Router agent Agent today
As an agent
Reads the message and decides: general, simple data, complex or workflow. Rewrites follow-ups so they stand alone.
Where it may go wrong
Sends a complex comparison down the simple path (wrong or incomplete answer), or a simple question down the slow path. Mis-resolves 'that' or 'same period'.
Why that is not good
Classification needs language understanding, so a model is the right tool. It is a good agent, but its choice must be safe to get wrong.
What our code does
The route is one short call. If the standalone question is missing, the user's own text is used. A fast-path failure falls back to the full agent loop.
How that helps
A wrong route costs time, not safety: every path ends in the same guarded SQL and number check.
3. Entity agent Code first, agent only when unclear
As an agent
Reads text like 'UK3' or 'Cars USA Shipping' and decides which stored entity it means.
Where it may go wrong
Invents a plausible code that does not exist. Picks UK03 when the user meant UK3. Quietly chooses one of two similar entities.
Why that is not good
A wrong entity gives a correct-looking number for the wrong company. Models are confident when they guess.
What our code does
Fuzzy match against the real stored values, with a score. Ties are flagged as ambiguous. Values are cached at startup.
How that helps
Only values that exist can be used, and ambiguity is surfaced instead of guessed. The lookup is cached, so no model call and no wait.
4. Period agent Code first, agent only when unclear
As an agent
Turns 'last quarter', 'Feb 25' or 'latest' into the right period for the right table.
Where it may go wrong
Mixes calendar and fiscal periods. Gets 'last quarter' wrong because it does not reliably know today's date. Picks a period that has no data.
Why that is not good
Dates are rules. A model applies them differently each time, and a wrong period is an easy quiet error.
What our code does
A date parser plus the period values that really exist in the data. 'Latest' is the newest period with data. Relative dates use one trusted date.
How that helps
The same words give the same period every time, and the period always exists in the data.
5. Table-finder agent Code first, agent on low confidence
As an agent
Chooses which tables answer the question.
Where it may go wrong
Names a table that does not exist, or one outside the user's domains. Chooses a different table for the same question on different days.
Why that is not good
Table choice drives every later step. Inconsistent choices make answers inconsistent.
What our code does
BM25 search over the written table pages, filtered by the user's role. On complex questions the catalog agent explores further.
How that helps
Fast and repeatable. Only tables the user may see are offered, so access holds before any SQL is written.
6. SQL-writer agent Agent today
As an agent
Writes the query from the question, table pages, resolved values and examples.
Where it may go wrong
Wrong join key, wrong filter value, a column that does not exist, or a long query that is slow to write.
Why that is not good
This is real reasoning, so an agent is right. The mistake would be trusting its output without checks.
What our code does
One SQL writer call, then a guarded run. One repair attempt on an error or empty result. Output is kept short (phase 2).
How that helps
A wrong query fails or is caught by the guards. The model never runs SQL directly.
7. SQL-safety agent Must stay code
As an agent
Reads the proposed SQL and decides whether it is safe to run.
Where it may go wrong
Approves a query it should refuse, especially if the question or a table value contains instructions that talk it into it. May approve an UPDATE written cleverly.
Why that is not good
A rule written as a prompt can be argued with. Safety for finance data cannot depend on how persuasive a question is.
What our code does
Code checks inside the run tool (the seven checks on the Low-level page): read-only, allowed schemas, limits and budgets. The write-capable MCP tool is never called.
How that helps
Same verdict every time, whatever the model says. Each check has a unit test.
8. Access agent Must stay code
As an agent
Decides whether this user may see these tables or domains.
Where it may go wrong
Grants access after a persuasive request, or refuses inconsistently. Cannot be audited the same way twice.
Why that is not good
Access control is the clearest case for a fixed rule. A model's decision may differ between two identical requests.
What our code does
Role to domain mapping from the access config, applied on every tool call. A user with no role gets no data.
How that helps
One clear answer to 'who allowed this?', backed by a config file and tests.
9. Executor agent Code in our design
As an agent
Runs the query, waits, handles errors and returns the rows.
Where it may go wrong
Calls the wrong MCP tool (including the write-capable one), retries forever, misreads a 'still running' state as an error, or retypes values.
Why that is not good
There is no decision to make, so you only add cost and risk. An agent holding tool access is a bigger attack surface than a fixed client.
What our code does
A client that can call only two read tools, retries a dropped connection twice, polls with short first waits and converts types exactly.
How that helps
Predictable time, exact types (decimals stay decimals) and no path to a write.
10. Number-verifier agent Must stay code
As an agent
Reads the answer and the results and decides whether every number is supported.
Where it may go wrong
Misses a wrong number, or approves one that looks plausible. A model that wrote an error often cannot see it when it re-reads.
Why that is not good
A checker built from the same kind of model shares its blind spots, so it is not independent.
What our code does
Code extracts every number in the answer and compares it with cells, row counts, totals, calculation outputs and numbers in the question. Unsupported: one rewrite, then a caveat.
How that helps
Independent of the writer. Every number shown is either supported by a tool result or flagged.
11. Table-builder agent Must stay code
As an agent
Turns result rows into the 'Details' table for the user.
Where it may go wrong
Rounds or retypes a value, drops a row, reorders rows, or mislabels a column while copying.
Why that is not good
The number check reads the answer text, not table cells, so a changed cell would not be caught.
What our code does
Rows are copied straight from the result in code, up to a fixed limit.
How that helps
The table always equals the query result.
12. Answer agent Agent today
As an agent
Writes the business-language answer, how it was calculated, and follow-up questions.
Where it may go wrong
States a number that is not in the data, uses technical words, or returns JSON as text.
Why that is not good
Language is the model's strength. The risk is trust in the figures it writes.
What our code does
Gets only the query results as facts. JSON-as-text is recovered. Output then goes through the number check.
How that helps
Good wording from a model, with the numbers held to the data.
13. Memory-save agent Code in our design
As an agent
Decides what to store about the turn and writes it.
Where it may go wrong
Writes to the wrong table or column, stores something sensitive, forgets a field, or blocks the reply while writing.
Why that is not good
A missed or wrong write is a lost or wrong audit record. Writing to the wrong schema would be serious.
What our code does
A background writer that only writes to the app's own tables, checks each row against a fixed column list, and never delays the reply.
How that helps
Complete records, writes limited to one schema, and a failed write is recorded, not silent.
14. Trace agent Code in our design
As an agent
Summarises what happened in each step for logs.
Where it may go wrong
Leaves steps out or paraphrases them, so the log no longer matches what ran. May copy something sensitive into a log.
Why that is not good
A log written by a model is a story about the run, not a record of it.
What our code does
A tracer emits a structured event for every model call and tool call, with timings and token counts, to fixed sinks. Secrets are never written.
How that helps
Complete, comparable logs. This is what let us measure each step during the latency work.

6. How the hybrid stays agentic where it matters

Agents already in the design
  • Route: classify every request.
  • SQL writer: one query, one repair attempt.
  • Supervisor with catalog, SQL, analyst, knowledge and action agents for complex questions.
  • Answer writer: business-language answer.
  • Summary investigator: explains flagged changes.
Pattern for adding more: agent proposes, code disposes
  • An agent may suggest a table, a filter value or a repair.
  • Code checks it: allowed table, real value, safe SQL, supported number.
  • Only what passes reaches the user.
Good next uses of agents
  • Disambiguate entities when the match is unclear.
  • Pick tables when search confidence is low.
  • Offline evaluation: a model judges answers in tests, never in the live path.
Never agents
  • SQL safety and read-only limits.
  • Role and domain access.
  • Number verification.
  • Copying result rows into tables.
  • Writing to the store.

7. Talking points

  • We did not avoid agents. We placed them where judgment is needed and kept rules in code.
  • Code steps are faster, cheaper, repeatable and auditable. That matters for finance.
  • Every number shown comes from a query result and passes an independent check.
  • More autonomy can be added step by step, behind the same code checks, without a redesign.
  • Measured: phase 1 cut data-question time by about 20%. The main remaining cost is model output time, which a longer agent chain would multiply.

Measured: route call about 3 s, answer rewrite about 2.4 s, the 20 to 30 s range. Estimates for illustration: 2 to 4 s per extra agent, the 30 to 55 s total, the 45 to 75 s bar and the 69% example.
